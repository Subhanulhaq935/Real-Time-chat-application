PROJECT: REAL-TIME CHATTING WEBSITE
Complete Master Prompt + Phase-by-Phase Prompts
================================================

PROJECT OVERVIEW
----------------
Build a secure, responsive, real-time, one-to-one text chatting website using React and FastAPI.

Initial scope:
- Signup using email address and password.
- Verify email ownership using a one-time password (OTP) sent by email.
- Login securely.
- Search for registered users by exact email address.
- Start private one-to-one conversations.
- Send and receive text messages in real time.
- Store messages in PostgreSQL so chat history remains available.
- Allow users to give contacts custom names that only they can see.
- Logout securely.
- Make the website installable on supported laptop and mobile browsers as a Progressive Web App (PWA).

IMPORTANT: Image and file sharing are NOT part of the initial implementation. Add image sharing later in a separate phase without breaking existing features.

RECOMMENDED TECHNOLOGY STACK
----------------------------
Frontend:
- React
- Vite
- JavaScript
- React Router
- Axios or Fetch API
- Responsive CSS
- vite-plugin-pwa

Backend:
- Python
- FastAPI
- Uvicorn
- SQLAlchemy 2.0
- Pydantic
- Alembic for database migrations
- PostgreSQL
- WebSockets for real-time messaging
- SMTP for verification emails
- Secure authentication using either JWT with an appropriate delivery mechanism or secure server-side sessions

Testing:
- Pytest
- FastAPI TestClient or HTTPX
- Appropriate frontend testing tools

Use compatible, stable package versions and provide exact installation commands.

3. BACKEND ARCHITECTURE

Follow a clean layered architecture:

- routers: HTTP endpoints and WebSocket routes
- services: business logic
- repositories: database operations
- models: SQLAlchemy database models
- schemas: Pydantic request and response schemas
- core: configuration, security, and authentication utilities
- db: database engine, session management, and base model
- websockets: connection management and real-time message delivery

Dependency flow:
Router -> Service -> Repository -> Database

Services should not contain unnecessary SQL queries, and routers should not contain business logic. Use dependency injection for database sessions and authenticated users.

4. DATABASE REQUIREMENTS

Create relational database tables for:
- users
- email_otps
- conversations
- conversation_participants
- messages
- contacts

Use appropriate primary keys, foreign keys, unique constraints, indexes, and timestamps.

Requirements:
- Email addresses must be unique and consistently normalized.
- Passwords must be stored as secure password hashes, never as plain text.
- Unverified accounts must not be allowed to use the chat.
- OTP records must expire and cannot be reused.
- Private conversations must have exactly two participants.
- The same pair of users must not accidentally create duplicate conversations.
- A message must belong to an existing conversation and an authenticated sender who participates in it.
- Custom contact names must be private to the user who sets them.
- Messages must persist in PostgreSQL.
- Use Alembic migrations rather than automatic table creation in production.

Explain the relationships between all tables and why junction tables are required.

5. SECURITY REQUIREMENTS

- WebSocket authentication and conversation membership checks.
- Safe CORS configuration.
- Secure session or token handling.
- Appropriate database transaction handling.
- Generic authentication errors where necessary to reduce account enumeration.
- Logout and session/token expiration handling.

Never expose passwords, OTP secrets, email credentials, or authentication tokens in logs or frontend source code.

7. REAL-TIME MESSAGING REQUIREMENTS

Use WebSockets for real-time delivery.

The backend must:
- Authenticate each connection.
- Verify that the user belongs to the requested conversation.
- Validate each message.
- Save a message to PostgreSQL before confirming successful sending.
- Deliver the message to the authorized recipient.
- Handle disconnected users.
- Clean up closed connections.
- Support reconnecting and loading missed messages through the message-history API.

Do not rely on WebSockets alone for message persistence.

8. CONTACT RENAMING

Implement a contacts table with:
- owner_user_id
- contact_user_id
- custom_name
- created_at
- updated_at

A custom name belongs to the user who sets it. For example, if Ali renames Ahmed to "Best Friend", only Ali should see that label. Ahmed's account name and other users' views must not change.

Allow a user to create, update, and reset a custom name.

GENERAL DEVELOPMENT NOTES
-------------------------
- React, FastAPI, PostgreSQL, SQLAlchemy, Pydantic, and WebSockets can be used without license fees, but hosting and third-party service free tiers have limits.
- Gmail SMTP has account and sending limits. Use environment variables and never expose credentials.
- A PWA can be installed on supported devices but is not automatically an APK or Windows .exe.
- Public deployment normally requires HTTPS.
- Free hosting plans can have restrictions on sleeping, storage, bandwidth, database size, and usage.
- Keep all secrets out of source control.
- Use .env.example as a template and keep the real .env file private.
- Never store passwords or plaintext OTPs in the database.
- Test with at least two separate user accounts to verify private messaging.
- The initial project is text-only. Image storage is a future phase.
